## 1. 핵심 요약

1. **Phase 5의 수집 → 저장 → 태깅 → 조회 API → Home·Dev 화면 흐름은 코드로 완성되었고, 샘플 응답으로 검증되었습니다.**
   - [실행] 백엔드 203 passed, 프론트 29 passed, E2E 3 passed
   - 다만 **실제 외부 사이트에서 수집한 적은 한 번도 없습니다.**
     - [실행] 작업 환경의 네트워크가 외부 접속을 막아 `collect --dry-run`이 전부 `ProxyError`
     - [실행] 개발 DB의 `contents`·`job_runs`는 0건
   - 실데이터 품질(피드 생존 여부, 요약 품질, 태깅 정확도)은 아직 측정되지 않았습니다.
2. **본문은 저장하지 않습니다.**
   - 저장하는 것: 제목, 피드가 주는 짧은 설명(최대 300자), 링크, 작성자, 날짜, 소스 지표
   - 그래서 "뉴스 배경 설명", "실습 가이드" 같은 기능은 현재 데이터로는 근거가 부족합니다. 본문 확보 정책(저작권)과 LLM 사용 결정이 먼저 필요합니다.
3. **기술 분류(57개)는 Home·Dev·Career를 잇는 공통 ID로 쓸 수 있는 구조입니다.**
   - 다만 Career 쪽(트랙·단원)에는 아직 기술 ID 연결이 없습니다. 트랙 slug `python`과 기술 slug `python`이 이름만 같을 뿐 DB 관계는 없습니다.
   - 연결 테이블을 하나 추가하는 방식으로, 기존 학습 기록·API를 건드리지 않고 확장할 수 있습니다.
4. **태깅은 단어 일치 규칙이라 단순하고 예측 가능하지만, 의미를 이해하지 못합니다.**
   - [실행] 사례 점검에서 확인한 오탐: "컨테이너선"→Docker, "모니터링 인력 채용"→DevOps
   - [실행] 확인한 누락: "Go 1.25", "데이터센터", "게임 업계"
5. **트렌드 차트는 "언급 기사 수"일 뿐 동향 분석이 아닙니다.**
   - 비교 기준이 없고 매체별 기사량 편향을 보정하지 않습니다.
   - 집계 API는 기술 필터 칩과 향후 "급상승" 계산에 재사용할 수 있습니다.
6. **개인화의 기반은 일부 있습니다.**
   - 있는 것: `user_settings.personalization_enabled`, 기술 ID
   - 없는 것: 콘텐츠 API의 "로그인 시 사용자 정보 선택적 사용" 경로, 관심 기술·목표 테이블(Phase 6 예정)

### 2-2. 화면 구성

**Home (`/`)** — `HomePage.jsx`

- 제목과 `FeedUpdated`(마지막 갱신·지연 표시, `GET /api/feed-status?scope=news`)
- `TechFilter`: 칩 최대 12개 = 분야 + 기술. 칩 목록은 `GET /api/trends?scope=news`의 결과를 씁니다.
- `FeedList` + `ContentCard`: 뉴스 카드, 12개씩 "더 보기"(`GET /api/news?page&size&tech`)
- 트렌드: `RankBars` "분야별 기사 수", `RankBars` "많이 언급된 기술", `DailyTrend`(상위 5개 기술 일별 선 그래프 + 표 보기)

**Dev (`/dev`)** — `DevPage.jsx`

- `FeedUpdated`(`scope=dev`)
- `TechFilter`(기술만, 분야 제외)
- `ChannelTabs`(`GET /api/dev/channels`): DEV Community / Hacker News / Stack Overflow / GeekNews / 국내 기술블로그
- `SortToggle`: 최신순 / 주간 인기. 지표가 없는 RSS 채널은 인기순이 비활성입니다.
- `ChannelFeed` → `GET /api/dev/channels/{c}/posts?sort&days&page&size&tech`
- 카드 지표 이름은 채널 종류별 `METRICS`를 씁니다: blog = 반응·댓글, community = 포인트·댓글, qna = 점수·답변·조회
- 하단: `RankBars` "많이 언급된 기술", "분야별 글 수"

**표시 정책** [분석]

- 지표가 `null`이면 숨기고, `0`이면 표시합니다(`ContentCard`의 `metrics` 필터).
- 시간은 서버가 `Z`가 붙은 UTC로 보냅니다(`schemas/content.py` `UtcTime`). 화면에서는 `utils/relativeTime.js`로 "n분 전"처럼 표시합니다.

### 3-2. 실행 방식과 주기

- 실행: `uv run python -m app.jobs collect [--source slug] [--dry-run]` (`app/jobs/__main__.py`)
- **스케줄러가 없습니다.** 주기 실행(cron·워커 컨테이너)은 Phase 8 계획입니다. 지금은 사람이 실행해야만 데이터가 갱신됩니다. [분석]
- 한 번 실행하면 소스마다 순서대로 처리합니다. [분석]
  - 각 소스마다 MariaDB `GET_LOCK('devhub:collect:{id}', 0)`을 잡고, 이미 실행 중이면 `skipped`로 기록합니다.
  - 가져오기는 트랜잭션 밖에서, 저장은 소스당 트랜잭션 하나로 합니다.
- 소스당 최대 건수: `max_items` (기본 30, 기업 블로그 10). Dev.to는 요청 2회(최신 + 주간 인기)입니다.
- 1회 실행 시 외부 요청 수: 약 27회. [분석]

### 3-4. 실패·중복·오래된 콘텐츠

| 상황 | 처리 | 근거 |
| :--- | :--- | :--- |
| 소스 접속 실패, HTTP 오류 | 그 소스만 `job_runs.status='failed'` + 오류 요약, 다른 소스는 계속. 5xx·네트워크 오류는 1회 재시도 | [실행] `test_a_failing_source_is_recorded_and_does_not_stop_others` · `integrations/http.py` `HttpFetcher` |

| 오류 메시지 속 비밀값 | 쿼리 문자열을 빼고 기록 (Stack Exchange 키 보호) | [분석] `_where()` |

| 재수집 | `(source_id, url_hash)` UNIQUE, 새 글만 insert, 지표·제목 변경 시 update, 제목·설명·태그가 바뀐 경우만 재태깅 | [실행] |
| 여러 소스의 같은 링크 | **별도 행으로 보관** (소스별 지표 보존). 화면 탭이 달라 중복 노출은 제한적, 뉴스 매체 간 중복은 가능 | [분석] |
| 같은 사건, 다른 기사 | 묶지 않음 (유사 기사 판별 없음) | [분석] |
| 오래된 콘텐츠 | **삭제·만료 없음**. 목록은 최신순이라 자연히 뒤로 밀림. 인기순·트렌드만 기간(기본 7일) 필터 | [분석] |
| 피드에서 사라진 글 | DB에 남음 | [분석] |
| `job_runs` | 무기한 누적 | [분석] |
| 중단된 실행 | `running` 상태로 남을 수 있음. 화면 계산은 성공 기록만 써서 영향 없음 | [분석] |

### 3-5. 외부 서비스 제한과 운영 위험

| 대상 | 제한·조건 | 위험 |
| :--- | :--- | :--- |

## 4. 기술 분류·트렌드 분석 구조

### 4-1. 기술 분류 구조

**테이블** [분석]

- `technologies`: slug UNIQUE, name, kind, status(published/retired)
- `technology_aliases`: alias UNIQUE, technology_id, `tag_only`
- 파일: `backend/content/technologies.yaml`, 검증은 `taxonomy.py` `TechnologiesFile`(별칭 소문자화, 파일 전체 중복 금지)

**구성** [실행] YAML 집계

| 항목 | 수량·값 |
| :--- | :--- |
| 기술 수 | 57 |
| kind별 | field 12, language 12, tool 13, framework 10, platform 7, library 3 |
| 별칭 | 본문 일치 199개, 태그 전용 40개 |
| `field` | ai, frontend, backend, mobile, data, cloud, devops, security, database, blockchain, game, llm |

**구조적 한계** [분석]

- 계층(부모-자식)이 없습니다. 예: React → frontend, LLM → AI 관계를 표현할 수 없습니다. `llm`과 `ai`는 둘 다 `field`라 같은 기사가 둘 다 붙어도 관계가 없습니다.
- 버전·제품 수준 구분이 없습니다(Python 3.14 = Python).
- 분류 체계에 없는 주제는 잡지 못합니다. 예: 반도체, 데이터센터, 핀테크, 스타트업 투자.

### 4-2. 분류 방식 (`app/services/tagging.py`)

- 뉴스와 Dev 모두 같은 `Tagger`를 씁니다. `store_items` → `_tag`에서 `method='rule'`로 저장합니다.
- 입력은 `title` + `excerpt` + `source_tags`입니다.
- 본문 일치: 기술별 정규식 하나씩이고, 단어 경계는 영문·숫자 기준입니다.
  - 한글은 경계로 취급해 "파이썬은"과 일치합니다.
  - 기호로 끝나는 별칭("c++", "c#")은 뒤쪽 경계를 보지 않습니다.
- 태그 일치: 소스 태그를 소문자화하고 `#`과 버전 접미사(`-3.x`)를 지운 뒤 정확히 비교합니다. `tag_only` 별칭은 여기서만 씁니다(go, react, js 등).
- 신뢰도·근거 위치는 저장하지 않습니다. `content_technologies.method`만 있습니다.

### 4-3. 정확성 검증

[실행] 단위 테스트 (`tests/unit/test_tagging.py`)

- "java"는 "javascript"에, "ai"는 "OpenAI"에 일치하지 않습니다.
- 한글 조사가 붙어도 일치합니다. C++26·C#도 처리합니다.
- 태그 전용 별칭과 버전 접미사 처리를 확인했습니다.

[실행] 실제 `technologies.yaml`로 만든 태거로 **직접 작성한 헤드라인 18개**를 점검했습니다. 실수집 데이터가 아니므로 정확도 수치로 일반화할 수 없습니다.

| 결과 | 사례 |
| :--- | :--- |
| 기대대로 | "Python 3.14…"→python, "Azure outage…"→azure, "MySQL to PostgreSQL"→mysql·postgresql, "RAG 파이프라인"→llm, "Spring is coming: MacBook"→없음, "Swift payments network"→없음 |
| **오탐** | "물류 **컨테이너**선 운임 상승"→docker, "쿠팡 **모니터링** 인력 채용"→devops, "넷플릭스 신작 'Kubernetes 전쟁'"→kubernetes |
| **판단이 갈리는 경우** | "삼성전자 AI 반도체 HBM4"→ai (산업 뉴스도 AI로 집계), "개인정보 보호법 개정안"→security |
| **누락** | "Go 1.25 released"→없음 (`go`가 태그 전용), "데이터센터 이중화"→없음, "게임 업계 실적"→없음 (별칭이 "게임 개발"뿐), "iPhone… on-device AI"→ios 없음 |

**판단** [추정] 개발자 글(Dev.to·SO 등 태그 제공 소스)에서는 태그 덕분에 정확도가 비교적 높을 것입니다. 국내 뉴스는 산업·정책 기사가 많아 `ai`·`security` 같은 분야 태그가 넓게 붙고, 기술명 오탐·누락이 섞일 것입니다. 실데이터 수집 후 표본 검수(예: 소스별 50건)가 필요합니다.

### 4-4. 트렌드 API (`content_feed.py` `trends`, `GET /api/trends?scope&days`)

- 대상: 기간(`sort_at >= now - days`) 안의 범위(news/dev) 콘텐츠
- `fields`·`technologies`: 기술별로 **해당 기술이 태그된 콘텐츠 수**. kind로 분야와 기술을 나눕니다(상위 10개).
- `daily`: 날짜별 전체 건수 + 상위 5개 기술의 날짜별 건수. 날짜는 UTC 기준입니다.
- 화면 칩 목록도 이 결과를 씁니다.

### 4-5. 단순 언급 수와 기술 동향의 차이 [분석]

| 언급 수(현재) | 실제 동향 분석에 필요한 것 |
| :--- | :--- |
| 이번 기간의 절대 건수 | 이전 기간 대비 변화(증가율, 기준선 대비 이탈) |
| 기사량이 많은 매체가 결과를 좌우 | 매체·소스별 정규화(소스당 비중, 상한) |
| 같은 사건의 여러 기사가 모두 집계 | 사건 단위 묶기(유사 기사 군집) |
| 산업·정책 기사도 기술로 집계 | 기사 성격 구분(기술 내용 vs 시장 뉴스) |
| 하루 0~5건 수준의 작은 수 | 충분한 표본 또는 주 단위 집계 |

**재사용 가능한 부분**

- 기술 ID와 콘텐츠 연결(`content_technologies`), 기간별 집계 쿼리, 칩 목록
- "지난 N주 대비 이번 주 증가" 계산은 같은 테이블로 가능합니다(데이터 2~4주 축적 후).

## 6. 개인화 연동 가능성

### 6-1. 현재 기반 [분석]

- `user_settings.personalization_enabled` (기본 OFF, Phase 2에서 생성, 아직 어떤 기능도 이 값을 사용하지 않음)
- 기술 ID: 관심 기술의 대상으로 그대로 사용 가능
- Career 진행 기록: 완료 단원, 퀴즈 통과

### 6-2. 콘텐츠 개인화 추천

- 가능한 방식(규칙 기반, 소규모 확장): 관심 기술 태그가 붙은 콘텐츠를 앞에 두거나 별도 "관심 기술" 탭을 둡니다. 기존 `_with_technology` 필터를 여러 기술로 확장하면 됩니다.
- 학습 이력 반영: 완료 단원의 기술(5-4 연결 필요)과 콘텐츠 기술이 겹치면 가중치를 주는 방식이 가능합니다.
- 품질은 태깅 정확도(4-3)에 직접 의존합니다. [추정]

### 6-3. Career 추천과의 공통 구조

- 공통 축은 `technology_id`입니다.
- 콘텐츠도 학습 단원도 기술에 연결되면, "관심 기술 → (콘텐츠, 단원)", "목표 → 필요한 기술 → 미완료 단원" 같은 같은 구조의 질의가 가능합니다.

### 6-4. 개인화 OFF

- 현재 콘텐츠 API는 사용자 정보를 전혀 쓰지 않으므로 OFF여도 탐색은 그대로 동작합니다.
- 개인화를 추가할 때 **OFF면 현재 동작과 동일**하도록 설계하는 것이 자연스럽습니다(정책 결정 필요).

### 6-5. 관심 기술과 학습 목표의 구분

설계 문서 4-5의 후보 테이블 기준입니다. 정책으로 확정하지 않았습니다.

| 개념 | 성격 | 저장 |
| :--- | :--- | :--- |
| 관심 기술 | 보고 싶은 것 (가벼운 선호) | `user_interests` (기술 다수 선택) |
| 학습 목표 | 이루려는 것 (기간·상태 있음) | `learning_goals` |
| 현재 역량 | 할 줄 아는 것 (자기 평가) | `user_skill_assessments` |

콘텐츠 우선 노출은 관심 기술, 학습 추천은 목표·역량을 주로 쓰는 식으로 역할을 나눌 수 있습니다.

### 6-6. 개인화 구현을 어렵게 하는 현재 구조

[분석]

1. **선택적 인증 의존성이 없습니다.** `app/api/deps.py`에는 `get_current_user`(로그인 필수)만 있습니다. 공개 콘텐츠 API에서 "로그인했으면 개인화, 아니면 기본"을 하려면 선택적 사용자 의존성이 필요합니다.
2. **페이지 방식이 offset 기반입니다**(`_page`). 새 글이 수집되거나 정렬 기준이 개인화로 바뀌면 "더 보기"에서 중복·누락이 생길 수 있습니다. 커서 방식 검토가 필요합니다.
3. **태그 신뢰도가 없습니다.** 추천 가중치를 줄 근거가 "붙었다/안 붙었다"뿐입니다.
4. **정렬이 SQL 고정입니다**(`sort_at`, `score`). 개인화 점수를 섞으려면 계산 위치(쿼리 vs 애플리케이션)를 정해야 합니다.

[분석] 프론트

5. `usePagedList`와 페이지 컴포넌트가 로그인 상태를 의존성으로 쓰지 않아, 로그인·로그아웃 시 목록이 다시 로드되지 않습니다. Career의 `useMyResource` 같은 처리가 필요합니다.

## 7. 신규 기능별 구현 가능성 비교표

구분은 네 가지입니다: **현재 구현으로 가능** / **소규모 확장 필요** / **별도 개발 필요** / **현재 데이터로는 어려움**. "데이터 품질"은 구현 가능성과 별개로 결과가 쓸 만할지에 대한 평가입니다.

| # | 기능 | 구분 | 필요한 데이터 | 추가 개발 범위 | 기술적 위험 | 데이터 품질 평가 |
| ---: | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | 뉴스 배경·핵심 변화 설명 | **현재 데이터로는 어려움** (본문 확보 + LLM 필요 시 별도 개발) | 기사 본문 또는 충분한 요약, 배경지식 | 본문 확보 정책 결정 → LLM 연동, 출력 검증, 비용 상한, 저장 | 저작권, 사실 오류(환각), 비용, 지연 | 현재 제목 + 300자 설명만으로는 근거 부족 |

## 9. 기존 구조 재사용 및 확장 권장안

결정을 위한 선택지 정리이며, 확정안이 아닙니다.

**그대로 재사용할 것**

- 파일 기반 분류·소스 관리와 로더
- 어댑터 구조(`Fetcher` 주입, 샘플 응답 테스트)
- 실행기(잠금, 실행 기록, 실패 격리)
- 기술 ID와 콘텐츠 연결
- 공개 읽기 API 패턴

**작은 비용으로 효과가 큰 확장 후보**

1. 실데이터 수집 검증과 소스 정리(죽은 피드 제거, 표본 태깅 검수). 다른 모든 기능의 전제입니다.
2. 단원-기술 연결 + 기술별 공식 문서 목록(파일 관리) → 기능 2·5·6
3. 같은 기술의 다른 소스 콘텐츠 조회 → 기능 3·4(기술 일치 수준)
4. 선택적 인증 의존성 + 관심 기술 필터 → 기능 9 (Phase 6 테이블과 함께)

**별도 결정 후 진행할 것**

- 본문 확보 여부, LLM 도입(기능 1·7·8)
- 의미 기반 유사도(기능 4 고도화)
- 트렌드 표시 방식(유지/축소/급상승 전환)

**운영 보강 (Phase 8 후보)**

- 정기 실행, 실패 알림, Stack Exchange `backoff` 처리, `job_runs`·오래된 콘텐츠 보관 기간

## 10. 사용자와 추가 논의가 필요한 결정 사항

1. **Home·Dev의 역할**: "뉴스·글 모아 보기"에 머물지, Career로 이어지는 "학습 진입점"으로 둘지
2. **트렌드 차트**: 유지 / 축소(칩만) / 데이터 축적 후 "급상승" 방식으로 전환
3. **본문 처리**: 지금처럼 저장 안 함 유지 / 일부 발췌만 저장 / 설명 기능을 위해 처리 후 폐기 (저작권 검토 필요)
4. **LLM 도입 범위와 시점**: 요약·설명·관련성 판단 중 무엇을, 어떤 서비스로, 비용 상한은 얼마로 (Phase 6 AI 나침반 결정과 함께)
5. **공식 문서·학습 자료 관리 방식**: 사람이 파일로 관리 / 자동 수집
6. **단원-기술 연결 단위**: 트랙 단위 / 단원 단위
7. **개인화 OFF일 때 Home·Dev 동작**: 현재와 동일하게 할지
8. **관심 기술과 학습 목표의 화면상 구분 방식**
9. **수집 주기와 실행 환경**: 몇 시간마다, 어느 서버에서 (Phase 8)
10. **콘텐츠·실행 기록 보관 기간**
11. **소스 구성 확정**: 실데이터 확인 후 유지·제외할 피드, Hashnode 추가 여부
12. **실데이터 확인 방법**: 작업 환경 네트워크 허용 / 사용자 로컬에서 `collect --dry-run` 실행 후 결과 공유
13. **우선순위**: Career 콘텐츠 확충 / Phase 6 개인화 / Home·Dev 연결 기능 중 무엇을 먼저
