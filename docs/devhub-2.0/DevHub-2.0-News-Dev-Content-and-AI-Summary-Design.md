## 0. 전제 수정 (v1과 같음)

- P5-0 보고서와 비교 보고서는 "요약은 태깅이 부족할 때만, 또는 요약 표시가 제품 목표가 될 때만 검토"를 전제로 삼았습니다. 이 전제를 수정합니다.
- **AI 요약은 News와 Dev의 독립 제품 기능입니다.**
- 남은 선행 조건은 소스별 이용 허용 확인(8절)입니다.
- 태깅 품질 평가는 별도 트랙으로 유지합니다.
- 요약 결과는 태깅에 반영하지 않습니다(기본값).

### 제품 원칙

1. AI 요약은 원문을 대체하거나 사실을 보증하지 않습니다. 원문 열람을 판단하기 위한 사전 이해 수단입니다.
2. 카드의 목적지는 언제나 원문입니다. 요약이 없거나 실패해도 카드와 링크는 정상 동작합니다.
3. 개인화 추천은 P5 정책에 따라 별도로 진행합니다. 요약은 공개 목록의 정렬과 노출을 바꾸지 않습니다.
4. **(v2 추가)** 입력이 부족하면 AI 요약을 만들지 않습니다. 출처가 제공한 소개글을 AI 결과처럼 보이게 하지 않습니다.

## 1. News·Dev의 공통 기능과 차별화 요소 (v1과 같음)

### 1.1 2.0에서 실제로 공유하는 구조 [코드]

| 계층 | 공유 여부 | 근거 |
|---|---|---|
| 소스 정의 | 공유. `kind`와 `channel`로 구분합니다. | `ContentSource`, `backend/content/sources.yaml`. News 15개(모두 RSS), Dev 11개 |
| 수집 실행 | 공유 | `app/jobs/runner.py`, `app/integrations/{http,sources}.py` |
| 저장 | 공유. `UNIQUE(source_id, url_hash)` | `app/jobs/store.py::store_items` |
| 텍스트 정리 | 공유. `plain_text`(정규식으로 태그 제거, 300자) | `sources.py` |
| 태깅 | 공유. `Tagger`, `method='rule'` | `app/services/tagging.py` |
| 요약 컬럼 | 공유하지만 비어 있음. `contents.summary`, `summary_status`(`pending`만 기록) | `content.py`, `store.py` 97행 |

| 카드 UI | 공유. `ContentCard`, 새 탭, `noopener noreferrer` | `frontend/src/components/feed/ContentCard.jsx` |

### 1.2 차별화 요소

| 구분 | News | Dev |
|---|---|---|
| 요약이 답할 질문 | 무슨 일이 있었나 / 무엇이 바뀌나 / 왜 중요한가 / 주의점 | 기술 개념 / 구현 내용 / 적용 상황 / 주의점 |
| 같은 기사 중복 | 여러 소스가 같은 링크를 냄 → `url_hash` 그룹 | 소스별 독립(같은 링크가 드물게 겹침) |
| 구조 보존 필요도 | 낮음 | 높음(코드, 표, 제목, 경고) |
| 저작권 성격 | 언론 기사(소스별 UNVERIFIED) | 작성자 소유 글, CC BY-SA, 제3자 링크 |

### 1.3 Dev 요약 범위

- **1차 대상은 `kind=blog`**입니다. Dev.to와 국내 기술블로그 7개가 해당합니다.
- HN과 Stack Overflow는 `source_not_eligible`로 요약하지 않습니다.
- GeekNews는 사용자가 결정합니다(11절).

## 3. 공통 수집·본문 확보·AI 분석 아키텍처

### 3.1 전체 구조 [추정]

```
[수집] 기존 collect (변경 없음, LLM 호출 없음)
   RSS/API → contents (메타데이터, excerpt ≤300)
                    │
[요약 작업] summarize (별도 프로세스, CLI/스케줄)
   ① 대상 선정: 소스 허용, 기간, (kind, url_hash) 단위, 유효 요약 존재 여부
   ② 본문 확보: B1 피드 재수신 / B2 API 본문 / B3 HTML (허용 소스만) — 메모리에서만
   ③ 정규화·구조 보존 변환 + 생략 보고(omissions) + input_hash
   ④ 충분성 판정 → 미달이면 skipped (AI 요약 없음, 카드는 미리보기)
   ⑤ LLM 호출 (공통 클라이언트) → 스키마 검증 → 저장 (본문은 폐기)
                    │
[조회] 기존 API + ai_summary 필드 (done이고 유효할 때만, 그 외에는 null)
```

### 3.2 모듈 경계 (v1과 같음)

| 모듈 | 책임 | 공유 여부 | import 경계 |
|---|---|---|---|
| `integrations/http.py` (기존) | 외부 HTTP | 공유 | 웹 앱 금지 |
| `integrations/extract.py` (신규) | 본문 변환과 생략 보고 | 공유 | 웹 앱 금지 |
| `integrations/llm.py` (신규) | LLM 클라이언트, 키 지연 로드, 429·5xx 처리, 사용량 | 공유 | 웹 앱 금지, 수집기 금지 |
| `summaries/prompts/{news,dev}.py` | 프롬프트, 출력 스키마, 버전 | **분리** | 순수 모듈 |
| `summaries/policy.py` | 허용 판정, 대상 선정, 충분성, 유효성 | 공유 | 순수 모듈 |
| `jobs/summarize.py` | 실행 루프, 상태, 상한, 회로 차단 | 공유 | — |

### 3.3 미리보기와 AI 요약의 구분 (v2 신설)

| 구분 | 출처 제공 미리보기 | AI 요약 |
|---|---|---|
| 내용 | 피드나 API가 준 소개글(excerpt) **그대로** | 충분한 본문을 근거로 LLM이 정리한 구조화 결과 |
| 생성 주체 | 출처(언론사, 작성자) | LLM |
| LLM 사용 | **없음** | 있음 |
| 필요 입력 | excerpt(현행) | 본문 확보 단계 B1~B3 중 하나로 충분성 기준을 넘는 본문 |
| 카드 표기 | "출처 소개" (출처 이름 표시). AI 표기를 하지 않음 | "AI 요약" + 근거 표기 + 원문 확인 안내 |
| 지금 상태 | **이미 제공 중**(`ContentCard`의 excerpt) | 미구현 |

- **excerpt 기반 LLM 출력은 출시하지 않습니다.**
- PoC에서만 비교용 변형 `X0`으로 생성합니다. 목적은 "본문 기반 요약이 excerpt 대비 얼마나 나은가"와 "excerpt만으로 얼마나 과장하는가"를 재는 것입니다(9절).
- X0 결과는 화면에 노출하지 않습니다.

### 3.4 본문 확보 단계 (v2에서 재정의)

| 단계 | 경로 | 추가 요청 | 허용 조건 | 실패나 부재 시 |
|---|---|---|---|---|
| **B1** 피드 본문 | 요약 작업이 **소스 피드를 다시 받아**(소스당 실행 1회, 수집과 같은 `HttpFetcher`와 상한) 메모리에서 파싱합니다.<br>• `normalize_url(entry.link)`의 `url_hash`로 대상 `contents` 행과 맞춥니다.<br>• `entry.content[*].value`(RSS `content:encoded`, Atom `content`)를 가져옵니다. | 소스당 1회 | `body_level ≥ feed` | • 피드에서 빠진 글: B3(허용 시) → 아니면 `skipped: body_unavailable`<br>• 본문 없는 피드: 같음 |
| **B2** API 본문 | Dev.to 상세 API(글 1건당 1회, 마크다운 본문). 필드명, 요청 제한, 약관은 UNVERIFIED | 글당 1회 | `body_level ≥ api` | `skipped: body_unavailable` |
| **B3** HTML 본문 | 기사 HTML을 가져와 본문 영역을 추출. 단계별 검증(7.4절) | 글당 1회 + 리다이렉트 | `body_level = html`, robots 허용 | `skipped: body_unavailable` 또는 `extract_failed` |

**B1 일관성 규칙 [추정]**

1. **피드 항목과 `contents` 행의 대응을 확인합니다.**
   - `url_hash`가 같아야 합니다.
   - 정규화 제목(`plain_text`)이 `contents.title`과 같아야 합니다.
   - 제목이 다르면(기사 수정 또는 오매칭) 그 실행에서 요약하지 않고 `skipped: feed_mismatch`로 둡니다. 다음 수집 때 제목이 갱신되면 재시도합니다.
2. **피드 순환 문제가 있습니다.** 피드는 최근 N개만 담습니다. 수집 직후에 요약 작업을 실행해야 B1 성공률이 높아집니다. 스케줄은 "collect 다음 summarize"로 묶습니다.
3. **수집기와 요약기를 결합하지 않습니다.** 수집기가 본문을 메모리로 넘기는 방식(콜백)은 쓰지 않습니다. 수집기 장애와 요약기 장애가 서로 번지기 때문입니다.
4. **피드를 두 번 받는 비용**은 소스당 실행 1회입니다(TechCrunch [실측] 17.5KB).
   - 조건부 GET(ETag, Last-Modified)으로 줄일 수 있지만, 소스가 지원하는지 UNVERIFIED이고 선택 사항입니다.
5. 피드가 본문 전체를 주는지는 소스마다 UNVERIFIED입니다.
   - [실측 기반 추정] TechCrunch 피드는 건당 약 0.9KB라 본문 전체가 아닐 가능성이 높습니다.
   - PoC E1에서 소스별로 `entry.content` 유무와 길이를 집계합니다.
6. B1~B3 중 어떤 경로를 썼는지 `input_basis`(`feed_body`, `api_body`, `html_body`)에 기록합니다.

### 3.5 충분성 판정 (v2 강화)

| 종류 | AI 요약 생성 조건 [제안값] | 미달 시 |
|---|---|---|
| News | 본문(B1~B3) 정규화 후 **800자 이상**, 문단 3개 이상 | `skipped: insufficient_input` → 카드는 출처 제공 미리보기 |
| Dev | 본문 **1,500자 이상**, 그리고 생략 비율(5.3절)이 부분 입력 기준 이하 | 같음. 생략이 크면 `partial_input`으로 표시하거나 건너뜀(5.3절) |

- excerpt 길이는 조건이 되지 않습니다. v1의 "excerpt 120자 이상이면 T0 요약"은 **삭제했습니다**.
- 기준값은 PoC E2에서 본문 길이에 따른 품질 곡선을 보고 조정합니다.
- LLM이 `insufficient=true`를 반환하면(4.4절) 기준을 넘어도 `skipped: insufficient_input`으로 처리합니다.

### 3.6 대상 선정

1. 소스 `summary_level = body`, `llm_transfer = true`입니다.
2. Dev는 `kind=blog`만 대상입니다.
3. 최근 기간 이내입니다([제안값] News 7일, Dev 30일).
4. 해당 `(kind, url_hash)`에 **유효한** 요약(4.1.3절)이 없습니다.

## 4. 요약 저장 단위와 출력 스키마

### 4.1 저장 단위 (v2 재설계)

#### 4.1.1 요약의 주체를 `(kind, url_hash)`로 둡니다

| 대안 | 키 | 대표 변경 시 | 그룹 공유 | 조회 경로 | 판정 |
|---|---|---|---|---|---|
| v1 | `(content_id, kind)` | 새 대표의 `content_id`에 요약이 없어 다시 호출하거나 복사해야 함 | 별도 매핑 필요 | 대표 행 → 요약 | **폐기** |
| **v2** | `(kind, url_hash)` | **영향 없음.** 같은 URL 그룹이면 같은 요약 | 자연스럽게 공유 | 카드 행의 `url_hash` → 요약 | **채택** |

**근거 [코드]**

- `url_hash`는 정규화 URL의 SHA-256입니다(`store.url_hash`).
- News 그룹은 `row_number() over (partition by url_hash)`로 만들고, 기술 태그 합집합도 `url_hash IN (...)`으로 조회합니다(`content_feed._news_representatives`, `_news_group_technologies`).
- 같은 정규화 URL이면 같은 원문 페이지를 가리키므로, 요약도 공유할 수 있습니다.

**Dev**

- Dev 목록은 중복을 제거하지 않지만, 요약은 같은 URL이면 공유합니다(드묾).
- Dev 카드는 행마다 그대로 표시하고, 요약만 `url_hash`로 붙입니다.

**News와 Dev가 같은 URL을 가질 때**

- 예: 언론 기사와 커뮤니티 링크가 같은 URL을 가리키는 경우입니다.
- `kind`가 달라 요약도 따로 둡니다. 스키마가 다르기 때문입니다.
- HN처럼 요약 비대상인 소스의 카드에는 요약을 붙이지 않습니다. 조회 시 카드 소스의 허용 여부도 확인합니다(4.1.4절).

#### 4.1.2 테이블 초안 (확정은 F2, G1 이후)

```
content_summaries
  id                BIGINT PK
  kind              'news' | 'dev'                                  CHECK
  url_hash          CHAR(64)                                         -- contents.url_hash 값 (FK 아님)
  input_content_id  BIGINT NULL  FK contents.id ON DELETE SET NULL   -- 본문을 가져온 행(추적용)
  input_source_id   BIGINT NULL  FK content_sources.id               -- 허용 철회 판정용
  status            'pending' | 'running' | 'done' | 'failed' | 'skipped'   CHECK
  skip_reason       'source_not_eligible' | 'insufficient_input' | 'body_unavailable'
                    | 'extract_failed' | 'feed_mismatch' | 'not_allowed' | 'no_api_key'
                    | 'budget_exhausted' | 'refused' | NULL           CHECK
  schema_version    SMALLINT
  prompt_version    VARCHAR(32)
  model             VARCHAR(100)
  input_basis       'feed_body' | 'api_body' | 'html_body'            CHECK  (excerpt 없음)
  input_hash        CHAR(64)
  input_chars       INT
  omissions         JSON          -- 추출기가 기록 (5.3절). LLM 출력 아님
  partial_input     BOOLEAN
  payload           JSON NULL     -- 검증을 통과한 결과만
  error_code        VARCHAR(64) NULL
  attempts          SMALLINT
  next_attempt_at   DATETIME NULL
  tokens_in, tokens_out INT NULL
  generated_at, updated_at DATETIME
  UNIQUE (kind, url_hash)                    -- "현재 요약" 1행
```

- **이력 테이블을 두지 않습니다.** 재생성하면 같은 행을 덮어씁니다.
  - 이전 결과가 필요하면 PoC JSON이나 감사 로그로 남깁니다(결정 항목).
- `url_hash`는 `contents`에서 유일하지 않습니다(소스별로 중복). 그래서 FK로 만들 수 없습니다.
  - 그 대신 "`contents`에 해당 `url_hash`가 하나도 없으면 고아 행"으로 보고 정리합니다.
  - `contents`는 지금 삭제되지 않고 소스만 retire되므로, 고아 행은 실질적으로 생기지 않습니다 [코드].

#### 4.1.3 유효성과 재요약 기준

| 변화 | 기존 요약 | 재요약 | 이유 |
|---|---|---|---|
| 대표 기사 변경 (같은 `url_hash`) | **유효** | 하지 않음 | 같은 원문을 가리킵니다. |
| 새 본문의 `input_hash`가 다름 (기사 수정, 다른 소스 경로로 본문 확보) | **유효(표시 유지)** | 재요약 대기(`pending`). 기간 이내 글만 | 원문이 고쳐졌을 수 있습니다. 새 결과가 `done`이 되면 교체하고, 실패하면 기존 결과를 유지합니다. |
| 본문 변화 확인 주기 | — | 매 실행마다 확인하지 않음. **[제안]** 생성 후 48시간 이내 1회만 재확인 | 요청량과 비용을 줄입니다. |
| `prompt_version` 변경 (호환) | 유효 | 하지 않음(신규 글부터 적용) | 비용을 통제합니다. |
| `prompt_version` 변경 (품질 결함 수정) | **무효 표시 가능** | 기간 이내 글만 상한 안에서 재요약 | 결함이 있는 출력은 노출하지 않습니다. 버전마다 `invalidates: true/false`를 선언합니다. |
| `schema_version` 증가 | API 변환기가 지원하면 유효, 아니면 비표시 | 기간 이내 글만 | UI 호환 |
| `model` 변경 | 유효 | 하지 않음 | 모델만 바꿨다고 기존 결과가 틀리지는 않습니다. |
| 입력 소스의 허용 철회 (`summary_level` 또는 `llm_transfer`를 내림) | **즉시 무효(비표시)** | 하지 않음 | 법적·정책 변경입니다. 조회 단계에서 `input_source_id`의 현재 허용을 확인합니다. |
| 입력 소스 retire | 그룹에 보이는 행이 있으면 유효 | — | 원문 URL은 같습니다. 다만 `llm_transfer` 철회와는 구분합니다. |

#### 4.1.4 DB 제약과 조회 경로의 일치 [코드 확인 + 추정]

| 조회 | 현재 쿼리 [코드] | 요약 결합 방법 | 인덱스 |
|---|---|---|---|
| News 목록 | 대표 선정 `row_number() over (partition by url_hash ...)` → `Content.id IN (...)` 후 `sort_at` 정렬 | 페이지 행(최대 50)의 `url_hash` 목록으로 `content_summaries WHERE kind='news' AND url_hash IN (...)` 한 번 조회. `_news_group_technologies`와 같은 패턴 | `UNIQUE(kind, url_hash)`가 이 조회를 지원합니다. |
| News 그룹 기술 태그 | `contents.url_hash IN (...)` (전 소스 대상) | — | **[코드] `contents`에는 `url_hash`로 시작하는 인덱스가 없습니다.** 유일 제약은 `(source_id, url_hash)`이고, 인덱스는 `(sort_at, id)`, `(source_id, sort_at, id)`뿐입니다. 데이터가 쌓이면 그룹 쿼리 성능을 `EXPLAIN`으로 확인하고, 필요하면 `ix_contents_url_hash`를 추가합니다. 이 문제는 요약과 무관하게 기존에 있던 것입니다. |
| Dev 채널 목록 | `source_id` 필터 + `sort_at` | 페이지 행의 `url_hash`로 `kind='dev'` 조회 | 같음 |
| 표시 조건 | — | `status='done'` + 유효(4.1.3절) + **카드 소스와 입력 소스 모두** 현재 `summary_level=body` | `content_sources` 조인(소규모 테이블) |

- 정합성 규칙: 요약의 `url_hash`와 `kind`는 쓰기 경로(요약 작업)에서만 만듭니다.
- 조회 경로는 읽기만 합니다. 웹 앱은 `content_summaries`를 쓰지 않습니다(AST 경계).

### 4.2 News 요약 스키마 (v2: 근거 없는 항목은 null 또는 빈 배열)

```json
{
  "insufficient": false,
  "headline": "한 줄 요약 (≤ 60자, 필수)",
  "what_happened": "핵심 사건 (≤ 200자) 또는 null",
  "key_changes": ["주요 변화 (각 ≤ 120자)", "0~3개"],
  "why_it_matters": "원문이 직접 밝힌 의미 (≤ 200자) 또는 null",
  "caveats": ["원문이 밝힌 한계·조건·불확실성 (각 ≤ 120자)", "0~3개"],
  "entities": ["원문에 나온 기업·제품·기관명", "0~5개"],
  "technologies": ["허용 목록의 slug", "0~5개"]
}
```

### 4.3 Dev 요약 스키마

```json
{
  "insufficient": false,
  "headline": "한 줄 요약 (≤ 60자, 필수)",
  "article_type": "tutorial | case_study | concept | opinion | release_note | other",
  "key_concepts": [{ "name": "개념", "explanation": "≤ 120자" }],
  "implementation": null,
  "applicable_when": [],
  "caveats": [],
  "prerequisites": [],
  "technologies": []
}
```

- `key_concepts`는 0~4개입니다.
- `implementation`은 `{ "approach": "≤ 250자", "steps": ["0~5개"] }` 또는 `null`입니다. 원문에 구현 내용이 없으면 `null`입니다.
- `applicable_when`은 0~3개, `caveats`는 0~4개, `prerequisites`는 0~3개입니다. 모두 원문이 직접 언급한 것만 넣습니다.
- `code_languages`는 v1에서 LLM 출력에 있었지만, v2에서 **스키마에서 뺐습니다.** 추출기가 펜스 언어로 결정적으로 기록합니다(`omissions` 옆 `structure.code_languages`).

### 4.4 출력 공통 규칙 (v2 강화)

1. **원문에 명시되지 않은 항목은 `null` 또는 `[]`입니다.** 추론, 일반 지식 보충, "~일 것으로 보인다"류 서술을 금지합니다.
   - 프롬프트에 명시하고, 검증기에서 허용합니다(빈 값이 정상).
2. 필수는 `headline`뿐입니다.
   - 그 밖에 News는 `what_happened`, Dev는 `key_concepts`나 `implementation` 중 하나라도 있어야 표시합니다.
   - 모두 비어 있으면 `skipped: insufficient_input`입니다.
3. `insufficient: true`이면 다른 필드를 무시하고 `skipped`로 처리합니다. LLM이 입력 부족을 스스로 선언할 수 있게 하기 위해서입니다.
4. `why_it_matters`와 `caveats`는 **원문의 주장**만 담습니다. LLM의 평가나 전망이 아닙니다.
   - 원문이 의미를 밝히지 않았으면 `null`입니다.
5. 스키마에 맞지 않으면 1회 재요청합니다. 그래도 실패하면 `failed: schema_invalid`로 두고, 기본값으로 채우지 않습니다.
6. 길이 상한을 넘으면 실패로 처리합니다. 서버에서 자르지 않습니다.
7. `technologies`는 허용 목록과 교집합을 냅니다.
8. 검증기의 기계 점검: 출력에 있는 숫자, 버전 문자열, 날짜, 고유명사 토큰이 입력에 있는지 확인합니다.
   - 없으면 `unsupported_token` 경고를 남깁니다.
   - 출시 전에는 경고가 있는 결과를 표시하지 않습니다(9.4절).
9. 원문 텍스트는 데이터 블록으로 넣고 지시로 따르지 않게 합니다(프롬프트 주입 방지).

## 5. 본문 추출과 Dev 구조 보존

### 5.1 변환 형식 (v1과 같음)

- 제목 `h1`~`h4`는 `#`으로 표시합니다.
- 코드는 펜스와 언어를 유지합니다.
- 표는 마크다운 표로 바꿉니다.
- 경고 박스는 `> **주의:**`로 표시합니다.
- 이미지는 alt만 남기고, 내비게이션·광고·댓글은 제거하며, 링크는 텍스트만 남깁니다.
- 상한 [제안값]
  - 코드: 블록당 40줄
  - 표: 10행 × 6열
  - 전체: News 6,000자, Dev 12,000자
- 줄이는 순서: 코드 줄 → 표 행 → 뒤쪽 섹션 본문. 제목 계층은 끝까지 남깁니다.

### 5.2 추출 수단 [추정]

- B1: feedparser `entry.content` + 변환기
- B2: API 마크다운
- B3: 본문 영역 탐지 후보(`trafilatura`, `readability-lxml`)를 E1에서 비교해 선정합니다(의존성 미추가).
- 본문 영역을 찾지 못하면 페이지 전체 텍스트를 쓰지 않습니다(1.0 방식 금지). `extract_failed`로 처리합니다.

### 5.3 생략 보고와 부분 입력 판정 (v2 신설)

추출기는 변환할 때 **결정적인 생략 보고**를 함께 만듭니다. LLM 출력이 아닙니다.

```json
{
  "chars_before": 18240, "chars_after": 12000,
  "headings_total": 9,  "headings_kept": 9,
  "sections_total": 9,  "sections_truncated": 2, "sections_dropped": 0,
  "code_blocks_total": 6, "code_lines_total": 310, "code_lines_kept": 180,
  "tables_total": 2, "table_rows_total": 34, "table_rows_kept": 20,
  "code_languages": ["kotlin", "yaml"]
}
```

| 판정 [제안값] | 조건 | 처리 |
|---|---|---|
| 전체 입력 | 생략 없음 | 일반 요약 |
| 부분 입력 | 본문 생략 25% 초과, 또는 코드 줄 생략 50% 초과, 또는 잘린 섹션 1개 이상 | 요약 생성. `partial_input=true`. 카드에 "글 일부를 바탕으로 한 요약"을 표시 |
| 요약 불가 | 섹션 삭제 1개 이상, 또는 본문 생략 60% 초과 | `skipped: insufficient_input` |

**프롬프트 규칙**

- 생략 표시(`… (N줄 생략)`, `… (섹션 뒷부분 생략)`)가 있는 곳의 내용을 추측하지 않습니다.
- 생략된 코드의 동작을 서술하지 않습니다.

**생략으로 인한 요약 오류의 판단(평가 F5, 9.2절)**

1. **생략 민감도 시험 (E2):**
   - 전체 길이가 상한의 2배 이내인 Dev 글을 고릅니다.
   - ⓐ 전체 입력과 ⓑ 상한으로 줄인 입력으로 각각 요약합니다.
   - ⓑ에만 있는 진술 중 원문의 **생략 구간에만 근거가 있는 것**을 "생략 구간 추론(F5)"으로 셉니다. 원문 전체에는 있으므로 우연히 맞을 수 있지만, 입력에는 없었으므로 추론입니다.
   - ⓐ에는 있고 ⓑ에는 없는 핵심 항목은 "생략으로 인한 누락(F4)"으로 셉니다.
2. **검토자 점검:** 부분 입력 요약은 `implementation`과 `caveats`가 생략 구간의 내용을 서술하는지 확인합니다.
3. **기준 조정:** E2 결과로 5.1절의 상한과 부분 입력 기준을 조정합니다.

## 6. 원문 링크 이동 및 카드 UX

### 6.1 URL 처리와 원본 URL 보존 재평가 (v2 재작성)

#### 현재 동작 [코드]

- 수집한 URL은 `normalize_url`로 정규화한 뒤 `contents.url`에 **덮어써 저장합니다**(`store_items`의 `item.url = url`).
- 정규화 내용
  - 스킴과 호스트를 소문자로 바꿉니다.
  - `utm_*`, `fbclid`, `gclid`, `ref_src`로 시작하는 키를 제거합니다(대소문자 무시).
  - fragment를 제거합니다.
  - 빈 path는 `/`로 채웁니다.
  - 쿼리는 `parse_qsl` 후 `urlencode`로 다시 인코딩합니다.
- 카드는 이 값으로 이동합니다.
- 개발 DB의 수집 행은 **0건**입니다. 실수집이 아직 승인되지 않았습니다. 그래서 실제 소스 URL로는 아무것도 확인하지 못했습니다.

#### 로컬 실행 결과 [로컬 실행]

`normalize_url`을 합성 입력 19개로 실행했습니다(네트워크 없음).

| 입력 | 출력 | 의미 변화 |
|---|---|---|
| `?q=hello%20world` | `?q=hello+world` | 대개 없음. 폼 인코딩에서는 같은 값으로 해석합니다. 경로와 쿼리를 다르게 처리하는 서버는 UNVERIFIED |
| `?flag` | `?flag=` | **바뀔 수 있음.** 값 없는 키와 빈 값을 구분하는 서버가 있을 수 있음 |
| `?x=1;y=2` | `?x=1%3By%3D2` | **바뀜.** `;`를 구분자로 쓰는 서버에서는 파라미터가 달라짐 |
| `#section` | 제거 | 문단 앵커만 잃음. 기사 이동에는 영향 없음 |
| `/#/post/1` 형태(해시 라우팅). 직접 실행하지 않았고, `#section` 결과에서 유추함 | `#` 뒤가 제거됨 | **이동 대상이 바뀜.** 해시 라우팅 사이트라면 다른 페이지로 감 |
| `?q=가` | `?q=%EA%B0%80` | 없음(같은 값의 인코딩) |
| `https://Ex.com/CasePath` | 호스트만 소문자 | 없음(경로 대소문자 유지) |
| `https://ex.com` | `https://ex.com/` | 없음 |
| `?b=2&a=1`, `?tag=x&tag=y`, `?q=a+b`, `?q=%2B1`, `p%2Fq` | 그대로 | 없음(순서, 반복 키, 인코딩된 `+`와 `/` 유지) |
| `?utm_source=rss&id=5` | `?id=5` | 없음(의도한 추적 파라미터 제거) |
| Medium `?source=rss----…` | 그대로 | 없음(제거 목록 밖) |

#### 평가

- 링크가 손상될 수 있는 유형은 **세 가지**입니다.
  - `;` 구분 쿼리
  - 값 없는 키
  - 해시 라우팅
- **26개 소스에서 이 유형이 실제로 나오는지는 UNVERIFIED입니다.**
  - 테스트 픽스처의 URL은 모두 `utm_*` 사례입니다 [코드].
  - 실측 3개 소스는 URL 문자열을 기록하지 않았습니다.

#### 대안

| 대안 | 내용 | 마이그레이션 | 장점 | 단점 |
|---|---|---|---|---|
| **U0 현행 유지** | 정규화 URL을 저장하고 그 URL로 이동 | 없음 | 변경 없음. 추적 파라미터 없는 깔끔한 링크 | 위 세 유형이 실제로 있으면 링크가 손상됨 |
| **U1 저장값만 원본으로** | `contents.url`에는 원본(스킴 검증 후, 추적 파라미터만 문자열 수준에서 제거하고 재인코딩하지 않음)을 저장. `url_hash`는 지금처럼 정규화 URL로 계산 | **없음**(`store.py`와 테스트만 변경) | 손상 유형 제거, 중복 제거 동작 불변 | 기존 행은 정규화 값 그대로(현재 0건). 같은 그룹 안에서도 행마다 URL 문자열이 다를 수 있음(대표 행 URL로 이동하므로 무해) |
| **U2 `contents.source_url` 추가** | 정규화 URL과 원본을 모두 보존 | 필요 | 비교·감사 가능, 롤백이 쉬움 | 저장량과 스키마가 늘어남. 조회 코드 변경 |

#### 결정 방법 (v2)

1. **어느 대안도 지금 필수가 아닙니다.**
2. 실수집이 승인되면 **DB를 바꾸지 않는 측정 스크립트**로 판단합니다.
   - 어댑터 응답을 `collect --dry-run`과 같은 경로로 메모리에서 받습니다.
   - 원본과 정규화 결과를 비교합니다.
   - 위 세 유형의 건수를 소스별로 셉니다.
3. **판정**
   - 세 유형이 0건이면 U0을 유지합니다.
   - 1건 이상이면 U1을 채택합니다(마이그레이션 없음).
   - U2는 감사나 비교가 별도로 필요할 때만 씁니다.

#### 기타 URL 처리 (v1과 같음)

- API 어댑터에 `http/https` 스킴 검증을 추가합니다(비교 보고서 Phase A).
- 카드 링크에는 리다이렉트 최종 URL을 쓰지 않습니다.
- 클릭 추적용 중간 경유(`/out?url=`)는 만들지 않습니다.
- 이동은 지금처럼 `target="_blank" rel="noopener noreferrer"`입니다.

### 7.1 1.0 문제의 재발 방지 (v1 표 + v2 수정)

### 7.2 동시 실행과 상태 (v1과 같음)

- 잠금은 `GET_LOCK('summarize:<kind>')`입니다.
- 상태 전이: `pending → running → done | failed | skipped`.
- `running`이 30분 넘게 남아 있으면 `pending`으로 되돌립니다 [제안값].

### 7.3 비용 추정 (v1과 같음)

- 일일 호출 수 ≈ (News 신규 그룹 + Dev blog 신규 글 중 충분성 통과분) × (1 + 재요청률)
- 충분성 판정으로 실제 호출 수는 v1 추정보다 줄어듭니다. 줄어드는 비율은 UNVERIFIED이고 PoC에서 측정합니다.
- 단가는 공급자와 모델이 정해진 뒤 현행 가격표로 계산합니다.

### 7.4 보안 (v2: HTML 요청 단계별 검증 추가)

#### B3 HTML 요청 단계별 검증

| 단계 | 검증 |
|---|---|
| ① 후보 URL | • 스킴은 `https`만 허용 [제안]. `http`는 허용 목록에 명시된 소스만<br>• userinfo(`user:pass@`)를 거부합니다.<br>• 포트는 기본값만 허용합니다.<br>• 호스트는 그 소스의 `allowed_hosts`(YAML에 명시. 예: `techcrunch.com`)와 정확히 일치하거나, 명시된 하위 도메인이어야 합니다.<br>• IP 리터럴 호스트를 거부합니다. |
| ② 주소 해석 | • 호스트의 모든 A/AAAA 결과가 공인 주소여야 합니다. 사설, 루프백, 링크로컬, 멀티캐스트, 예약 대역(`ipaddress`의 `is_global`)이면 거부합니다.<br>• **연결한 실제 주소도 확인합니다.** DNS 재바인딩 대비로, 응답의 서버 주소를 확인하거나 검증한 IP로 연결을 고정합니다. 구현 방식(httpx 전송 계층 확장 등)은 F3에서 확정하며 UNVERIFIED입니다. |
| ③ 리다이렉트 | • 자동 추적을 끕니다(`follow_redirects=False`). 최대 3회까지 수동으로 따라갑니다 [제안값].<br>• 매 `Location`마다 상대 경로를 해석한 뒤 ①과 ②를 다시 통과해야 합니다.<br>• `https`에서 `http`로 내려가면 거부합니다.<br>• 허용 호스트 밖으로 나가면 중단합니다(`extract_failed: redirect_offsite`). |
| ④ 응답 | • `200`만 처리합니다.<br>• `Content-Type`이 `text/html` 계열이어야 합니다.<br>• 크기 상한은 2MB입니다 [제안값]. 지금 수집 상한은 5MB입니다.<br>• 타임아웃은 기존 설정을 따릅니다.<br>• 쿠키를 저장하거나 보내지 않습니다.<br>• JS를 실행하지 않습니다. |
| ⑤ 운영 예절 | • 호스트별 `robots.txt`를 실행마다 1회 받아 캐시하고, 거부된 경로는 건너뜁니다.<br>• 호스트당 요청 간격을 둡니다(5초 [제안값]).<br>• 정직한 User-Agent(`collector_user_agent`)를 씁니다.<br>• 자동화 탐지 회피는 하지 않습니다. |
| ⑥ 기록 | 최종 호스트와 홉 수만 기록합니다. 최종 URL은 카드 링크로 쓰지 않습니다. |

- 클라우드 세션의 egress 허용 목록이 바깥쪽 통제를 하나 더 제공합니다. 그렇다고 앱 검증을 생략하지 않습니다.

#### 기타 보안 (v1과 같음)

- 키는 환경변수로만 받고, 로그와 `job_runs`에 넣지 않습니다. CI에는 키를 두지 않습니다.
- 프롬프트 주입: 원문을 데이터 블록에 넣고, 도구는 쓰지 않으며, 출력을 JSON 스키마로 제한합니다. `technologies`는 허용 목록과 교집합을 냅니다.
- 외부 LLM 전송은 `llm_transfer=true`인 소스만 합니다. 사용자 데이터는 보내지 않습니다.
- 출력은 React 텍스트로 렌더링합니다.

## 8. 소스별 robots.txt·약관·저작권·외부 LLM 전송 구분 (v1과 같음)

- 26개 소스 모두 robots.txt, 이용약관, 저작권(요약 표시와 본문 일시 처리), 외부 LLM 전송이 **UNVERIFIED**입니다.
- 소스 YAML에 필드를 추가합니다. 기본값은 모두 불허입니다.
  - `summary_level`: `none` / `body` (v2에서 `excerpt` 단계는 삭제)
  - `body_level`: `none` / `feed` / `api` / `html`
  - `llm_transfer`: `false` / `true`
  - `allowed_hosts`: v2 추가
  - `review`: 검토일, 근거 URL, 검토자
- 검토가 비어 있는데 허용 값이 있으면 로더가 거부합니다.

| 소스 묶음 | 개수 | 4개 항목 | 비고 |
|---|---|---|---|
| 국내 언론 | 7 | UNVERIFIED | 전재 금지 문구가 흔하지만 사이트별로 확인하지 않음 |
| Korea IT Times | 1 | UNVERIFIED | — |
| 해외 언론 | 7 | UNVERIFIED | TechCrunch는 접근 가능 [실측]. 접근 가능하다고 이용이 허용되는 것은 아님 |

  4. 법적 판단은 사용자가 합니다.

## 9. PoC 범위와 검증 기준 (v2 재작성)

### 9.1 PoC는 정식 DB 변경 없이 진행합니다

| 항목 | 내용 |
|---|---|
| 실행 형태 | **실험 하네스 E1**. scratchpad 스크립트이며, 저장소에 커밋하지 않는 것이 기본입니다.<br>• 앱 모듈(`HttpFetcher`, `parse_feed`, `normalize_url`, `plain_text`, 태거)은 import해서 읽기 전용으로 씁니다.<br>• 앱 코드와 DB는 바꾸지 않습니다.<br>• 리뷰를 위해 저장소에 남기려면, `main`에 병합하지 않는 별도 브랜치(예: `poc/ai-summary`)를 쓸 수 있습니다. 이것은 승인 항목입니다. |
| 대상 행 | 개발 DB를 쓰지 않습니다. 하네스가 피드나 API를 직접 받아 메모리에서 표본을 고릅니다. 수집 경로와 같은 어댑터를 씁니다. |
| 결과 저장 | 로컬 JSON(`scratchpad/poc-summary/results/*.json`)에 다음만 남깁니다. **본문은 저장하지 않습니다.**<br>• 요약 출력<br>• `input_hash`, 길이, `omissions`<br>• 오류 코드, 토큰 수<br>• 검토자 판정 |
| 검토 자료 | 검토자는 원문 URL을 열어 원문과 대조합니다. 하네스가 원문 사본을 만들지 않습니다. |
| 화면 | 공개 화면에 노출하지 않습니다. 필요하면 로컬 정적 미리보기만 만듭니다. |
| 종료 | 결과를 보고한 뒤 파일 삭제 여부를 사용자에게 묻습니다. |
| 스키마 확정 | PoC 출력 JSON의 실제 사용 필드, `null` 비율, 상태 분포를 근거로 F2에서 테이블(4.1.2절 초안)을 확정합니다. |

### 9.2 오류 분류 (v2 신설)

| 코드 | 분류 | 정의 | 심각도 | 판정 방법 |
|---|---|---|---|---|
| **F1** | 사실 오류 | 원문과 **모순**되는 진술 (주체, 행위, 결과가 반대이거나 다름) | 치명 | 검토자가 원문과 대조 |
| **F2** | 숫자·버전·날짜·고유명사 오류 | 수치, 버전, 날짜, 금액, 인명·제품명이 원문과 다름 | 치명 | 검증기 `unsupported_token` 경고 + 검토자 확인 |
| **F3** | 근거 없는 설명 | 원문에 **없는** 내용 (일반 지식 보충, 추측, 전망, LLM의 평가). 사실일 수 있어도 오류로 셈 | 중대 | 진술마다 근거 문장을 찾는 방식 |
| **F4** | 핵심 내용 누락 | 검토자가 **요약을 보기 전에** 원문에서 뽑은 핵심 1~3개 중 빠진 것 | 중대 (첫 번째 핵심이 빠지면) / 경미 | 사전 핵심 목록과 대조 |
| **F5** | 생략 구간 추론 | 입력에서 생략된 부분에만 근거가 있는 진술 (5.3절) | 중대 | 생략 민감도 시험 + `omissions` 대조 |
| **F6** | 형식·표현 위반 | 길이·스키마 위반, 주장을 사실로 단정(원문은 "계획", 요약은 "출시"), `null`이어야 할 항목을 채움 | 경미 (단정 표현은 중대) | 검증기 + 검토자 |

- **판정 절차**
  1. 검토자는 원문을 먼저 읽고 핵심 목록을 적습니다.
  2. 요약을 진술 단위로 나눠 "지지됨 / 근거 없음 / 모순" 중 하나로 표시합니다.
  3. 누락을 확인합니다.
- **검토자 간 일치도**: 표본 일부를 두 명이 판정해 일치율을 보고합니다. 검토자가 한 명뿐이면 그 한계를 함께 적습니다.

### 9.3 탐색적 PoC (E2) — 판정 G1

| 항목 | 내용 |
|---|---|
| 표본 | 소스 3개 × 10건 = **30건** [제안값]. TechCrunch(News), Dev.to(Dev), 국내 기술블로그 1개(Dev) |
| 변형 | • 같은 글마다 ⓐ 본문 기반 요약(B1/B2/B3 중 가능한 것)<br>• ⓑ 비교용 `X0`(excerpt만, 출시 안 함)<br>• Dev 일부는 ⓒ 생략 민감도 쌍 |
| 측정 | • 오류 분류별 건수(F1~F6)<br>• 유용성("원문을 읽을지 판단하는 데 도움이 되는가", 1~3점)<br>• 상태 분포(`body_unavailable`, `insufficient_input` 비율)<br>• B1 성공률(소스별 `entry.content` 유무와 길이)<br>• 건당 토큰<br>• 두 번째 실행 호출 수 |
| G1 진행 기준 [제안값] | • 치명(F1, F2) 0~1건<br>• 중대 오류가 있는 요약 6건(20%) 이하<br>• 본문 기반 유용성 평균이 `X0`보다 높음<br>• 두 번째 실행 LLM 호출 0건<br>• 실패 주입 시 카드·링크 정상(가짜 클라이언트 테스트) |
| G1 결과 | 진행 / 소스나 입력 단계 축소 후 진행 / 중단 중 하나. 스키마와 충분성 기준 확정 |

**30건의 한계 (명시)**

- **통계적 한계**: 오류가 0/30이어도 95% 신뢰 상한은 약 10%입니다(3/n 근사). 실제 오류율이 10%여도 30건 안에서 0건이 나올 수 있습니다.
- **대표성**: 소스 3개, 언어 2개, 기간도 짧습니다. 26개 소스와 다른 시기의 글에 일반화할 수 없습니다.
- **검토자 편향**: 검토자가 적고 설계자가 검토를 겸할 수 있습니다.
- **용도**: G1은 **방향 판단**(계속할 가치, 입력 단계, 스키마)에만 씁니다. **출시 근거로 쓰지 않습니다.**

### 9.4 출시 기준 (G2, 정식 구현 후)

| 항목 | 기준 [제안값] |
|---|---|
| 표본 | 출시할 소스마다 20건 이상, 합계 **150건 이상** |
| 치명 오류 (F1, F2) | **0건 / 150건** (95% 상한 약 2%) |
| 중대 오류 (F3, F4 핵심, F5, 단정 표현) | 중대 오류가 있는 요약 **5% 이하** |
| 검증기 경고 | `unsupported_token` 경고가 있는 결과는 표시하지 않음(자동 비표시) |
| 실패 대체 | E2E: 모든 상태(`done`, 무효, `pending`, `failed`, `skipped`, `null`)에서 카드와 원문 링크 정상 |
| 운영 통제 | 비용 상한, 회로 차단, 키 없음 처리 테스트 통과 |
| 소스 허용 | 출시 소스 전부 `review` 기록과 사용자 승인 |
| 비출시 조건 | 어느 소스든 치명 오류가 나오면 그 소스는 출시에서 빼고 원인을 분석 |

### 9.5 출시 후 감시 (G2 이후)

- 주 1회, 표시 중인 요약에서 20건을 표본으로 뽑아 같은 분류로 검토합니다 [제안값].
- 치명 오류가 나오면 그 소스의 요약 표시를 즉시 끕니다. `summary_level`을 내리면 4.1.3절에 따라 바로 비표시됩니다.
- 사용자 오류 신고 버튼은 새 기능이므로 별도로 결정합니다(11절).
- 요약은 원문을 대체하지 않고 사실을 보증하지 않습니다. 카드 문구(6.2절)를 유지합니다. 감시 결과가 좋아도 "검증됨" 같은 표현으로 바꾸지 않습니다.

### 10.1 순서와 병행

```
E0 ─▶ E1 ─▶ E2 ─▶ G1 ─▶ F2 ─▶ F3 ─▶ F4 ─▶ G2 ─▶ F5
        F1(수집 안정화) ── E0 이후 언제든, F2 전에 완료
        P5-0 태깅 평가(라벨링) ── E1~E2와 병행
```

- **E1에 최소 본문 추출이 들어가므로**, 입력 단계 비교는 E2에서 할 수 있습니다. v1의 선후 충돌을 해소했습니다.
- E1 코드는 버리는 것을 전제로 합니다. F3은 E1의 결과를 바탕으로 다시 작성하며, 테스트와 보안 검증을 완비합니다.
- **정식 DB 변경은 F2 한 번뿐입니다.** G1 이후입니다.

### 10.2 P5 일정 영향 [추정]

- **기술 의존 없음.** P5 추천은 태깅과 P4 프로필을 쓰고, 요약은 쓰지 않습니다.
- **공유 작업:** F1은 P5 선행 작업과 같습니다. 한 번만 하면 됩니다.
- **실험 트랙(E0~E2)은 앱 코드와 DB를 바꾸지 않습니다.** 그래서 P5-0 태깅 평가와 병행할 수 있습니다.
- **충돌 지점:** F4의 `ContentItem`과 `ContentCard` 변경은 P5 추천 화면과 같은 컴포넌트를 건드립니다. 둘 중 하나를 먼저 병합하고 다른 쪽을 그 위에 얹습니다.
- **지연:** 요약을 먼저 출시하면(F2~F4, G2) P5 추천 착수가 그만큼 늦어집니다. P5를 먼저 하려면 E2와 G1까지만 진행하고 F2 이후를 P5 다음으로 둘 수 있습니다(11절 13번).
- **P5 정책 영향:** 없습니다(요약은 비개인화이며 공개 정렬을 바꾸지 않음).
