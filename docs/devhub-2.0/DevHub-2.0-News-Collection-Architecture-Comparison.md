## 2. DevHub 2.0 실제 수집 파이프라인 [코드]

```
python -m app.jobs collect [--dry-run] [소스...]
 └ Collector.run(source)                         app/jobs/runner.py
    ├ SELECT GET_LOCK('collect:<slug>', 0)       같은 소스 동시 실행 방지(실패 시 skipped 기록)
    ├ job_runs INSERT (running)                  자체 트랜잭션
    ├ adapter(fetcher, config)                   app/integrations/sources.py
    │   ├ collect_rss            → parse_feed (feedparser, 링크 http/https만 허용, excerpt 300자)
    │   ├ collect_devto          → /api/articles (최신 + top_days 인기글, external_id로 중복 제거)
    │   ├ collect_hackernews     → hn.algolia.com /search (url이 없으면 HN 토론 페이지)
    │   └ collect_stackoverflow  → api.stackexchange.com /2.3/questions
    ├ store_items(db, source, items, tagger)     app/jobs/store.py, 소스별 단일 트랜잭션
    │   ├ normalize_url (utm_/fbclid/gclid/ref_src 제거) → url_hash(SHA-256)
    │   ├ 새 글은 INSERT, 기존 글은 지표 갱신
    │   └ Tagger.match(title, excerpt, source_tags) → content_technologies(method='rule')
    └ job_runs UPDATE (succeeded/failed, 건수, error_summary)
```

### 2.1 장애 처리

| 동작 | 근거 |
|---|---|
| 소스 하나가 실패해도 예외를 밖으로 던지지 않고 `job_runs`에 기록한 뒤 다음 소스로 넘어갑니다. 소스 단위로 장애가 격리됩니다. | `runner.py::_run_locked`, `except Exception` 한 곳 |
| 재시도는 총 2회이며, 5xx와 전송 오류에만 적용합니다. 4xx와 429는 재시도하지 않습니다. | `http.py::_RETRY_STATUSES`, `_ATTEMPTS` |
| 타임아웃은 `collector_timeout_seconds`(기본 15초)입니다. 응답이 5MB를 넘으면 중단합니다. | `HttpFetcher` |
| 오류 메시지에 쿼리스트링을 넣지 않아 API 키가 노출되지 않습니다. | `http.py::_where` |

### 2.2 남은 약점

1. **429 대응이 없습니다.** `Retry-After`를 읽지 않고, 재시도 사이에 backoff도 없습니다.
   - 4xx를 재시도하지 않는 것은 옳습니다.
   - 다만 429가 와도 같은 실행 안의 다음 소스가 같은 호스트를 계속 호출할 수 있습니다(Dev.to 소스가 둘인 경우).
2. **리다이렉트 상한이 httpx 기본값(20)에 맡겨져 있습니다.** 리다이렉트로 호스트가 바뀌어도 검증하지 않습니다.
3. **항목 하나의 오류가 소스 전체를 실패시킵니다.** `_devto_item`은 `article["url"]`, `article["title"]`을 직접 인덱싱합니다. 응답 하나에 필드가 빠지면 KeyError가 나고, 그 소스의 나머지 항목도 모두 저장되지 않습니다. (발생 가능성만 있고 실제로 관측되지는 않았습니다.)
4. **API 어댑터는 URL 스킴을 검증하지 않습니다.** RSS는 http/https만 허용하지만 API 어댑터에는 이 검사가 없습니다. 화면 출력 단계에서는 React가 `javascript:` URL을 막아 완화됩니다.
5. **`HttpFetcher`에는 테스트가 없습니다.** 어댑터 파싱은 고정 응답 파일로 테스트합니다.
6. **스케줄러가 없습니다.** CLI로 수동 실행만 합니다.

## 3. 기존 HTML 크롤링·AI 요약 구현 여부

### 3.1 HTML 크롤링: 있었습니다 [코드·이력]

| 함수 | 대상 | 방식 | 저장 |
|---|---|---|---|
| `home_service.fetch_html_items` | RSS가 3건 미만인 언론사 5곳의 홈페이지 | 앞쪽 `<a>` 20개 중 텍스트가 10자를 넘는 링크를 기사로 간주 | 기사 후보 |
| `home_service.fetch_content` | 모든 신규 기사 URL | `article`, `main`, `#articleBody` 같은 선택자로 찾고, 못 찾으면 페이지 전체 텍스트 | **`news_feed.content`(LONGTEXT)에 본문 전체를 저장** |
| `dev_scraper.crawl_okky` | okky.kr 기술 게시판 | Selenium headless로 렌더링 후 bs4로 카드 파싱 | 메타데이터 |
| `news_service.get_news_thumbnail` (1기) | Naver/Google 기사 | og:image를 찾고 HEAD로 확인 | 이미지 URL |

몇 가지는 코드로 확인됐습니다.

- **[코드]** `fetch_content`가 선택자를 찾으면 길이 제한이 없습니다. 선택자를 못 찾았을 때만 3,000자로 자릅니다.
- **[코드]** `fetch_html_items`는 내비게이션 메뉴 링크도 기사로 넣을 수 있습니다(텍스트 길이만 봅니다).

### 3.2 AI 요약: 있었습니다 [코드·이력]

| 분석 항목 | 1.0 최종(`home_service.analyze_article`) | Dev(`dev_scraper.summarize_text`) | 트렌드(`get_trend_recommendations`) |
|---|---|---|---|
| 호출 시점 | 수집 파이프라인 안. 신규 URL마다 동기 호출(본문 GET 다음) | **크롤링 중 모든 항목.** DB 중복 확인보다 먼저 호출 | **API 요청 시점.** 관심어마다 호출 |
| 입력 | 제목 + 본문 앞 2,000자. 본문이 50자 미만이면 제목만 | • OKKY: **제목만** (`content=None`)<br>• Dev.to: description | 관심어에 맞는 기사 제목 3개 |
| 본문 추출 | bs4 선택자 / 전체 텍스트 | 없음 | 없음 |
| 프롬프트 | summary(한국어 3문장), category(7종), keywords 3개를 JSON으로 요청. `response_format=json_object` | 한국어 3~4문장, temperature 0.3 | 2문장 트렌드 요약 |
| 결과 저장 | `news_feed.summary`, `category`, `keywords` | `dev_posts.summary` (업데이트 때 덮어씀) | 저장하지 않음(매번 새로 생성) |
| 키워드 매칭 | `public_home`이 keywords 컬럼 원문에 `ilike` | `build_personal_feed`가 title/summary에 `ilike '%tag%'` | `NewsFeed.title.ilike` |

### 4.1 정리 [추정]

**1.0의 잦은 오류와 복잡한 예외 처리는 외부 API 자체보다 구현 방식에서 온 것으로 판단합니다.**

- 외부 호출을 사용자 요청 경로에 둔 것(4, 5, 16번)
- 수집·본문·요약·저장을 한 루프에 묶은 것(6, 7번)
- 실패를 기본값으로 삼킨 것(8, 9번)
- 영구 오류까지 재시도한 것(1번)

외부 요인으로 확인된 것은 Velog의 불규칙한 404와 사이트마다 다른 HTML·날짜 형식뿐입니다. 네트워크 요인은 1.0 자료에서 확인할 수 없습니다.

참고로 이번 2.0 세션의 403 26건은 클라우드 세션의 egress 허용 목록 때문이었습니다(P5-0 보고서 6절). 이것도 코드 결함이 아닌 환경 요인입니다.

## 6. AI 요약 및 기술 분류 전략

2.0에는 LLM 기능이 없습니다. 아래는 **선택 가능한 설계일 뿐**이고 구현하지 않습니다.

| 기준 | ① 규칙 기반 분류 (현재 2.0) | ② 확보된 텍스트로 LLM 보조 분류 | ③ 본문 추출 + LLM 요약·분류 (1.0 방식) |
|---|---|---|---|
| 입력 | 제목, excerpt(≤300자), 소스 태그 | ①과 같음 | 기사 본문(추가 HTTP 필요) |
| 추가 네트워크 | 없음 | LLM API | 기사 GET + LLM API |
| 비용 구조 | 0 | 신규 기사 수 × 짧은 입력 | 신규 기사 수 × 긴 입력 + 본문 수집 |
| 오류 유형 | • 별칭 누락 → 재현율 저하<br>• 동음이의어(`go`, `rust`, `spring`) → 정확도 저하<br>• 2.0은 단어 경계 정규식과 `tag_only` 별칭으로 완화 | • 기술 목록 밖의 라벨 생성<br>• 일관성 없음<br>• 응답 형식 오류 | ②의 오류 + 본문 추출 실패 + **요약의 사실 오류** |
| 검증 가능성 | 결정적이어서 같은 입력에 같은 결과. 테스트로 고정할 수 있습니다. | 출력을 허용 기술 ID로 제한하면 검증할 수 있습니다. | 요약의 사실성을 자동 검증하기 어렵습니다(원문 대조 필요). |
| 품질 개선 효과 | **측정 전이라 알 수 없습니다.** | 측정 전이라 알 수 없습니다. ①보다 낫다고 가정하지 않습니다. | 측정 전이라 알 수 없습니다. |
| 법적 위험 | 낮음 | 기사 메타데이터를 외부 LLM에 전송합니다. 낮음~중간 | 본문을 외부로 전송·저장합니다. 높음 |

### 6.1 권장 순서 [추정]

1. **먼저 ①의 품질을 측정합니다(Phase B).** 실제 수집 데이터에서 표본을 뽑아 사람이 라벨을 붙이고 정확도, 재현율, F1을 계산합니다.
2. **②는 ①이 부족하다는 수치가 나왔을 때만 검토합니다.** 그때도 다음 조건을 둡니다.
   - 출력은 `technologies` ID 목록으로 제한합니다.
   - `method='llm'`으로 구분해 저장합니다. 이 값은 이미 `content_technologies.method`의 허용값(`TAG_METHODS`)에 있습니다.
   - 규칙 결과와 병합할지는 별도로 판단합니다.
   - 같은 라벨셋으로 ①과 비교합니다.
3. **③은 요약 표시가 제품 목표가 되고, 소스별 약관이 허용할 때만 검토합니다.**

LLM을 도입한다면 다음은 1.0의 교훈에서 나온 필수 조건입니다.

- 수집과 분리된 별도 작업으로 실행합니다(8절 Q5).
- 요약·분류 결과와 상태(`ok`, `failed`, `skipped`), 모델명, 프롬프트 버전, 입력 해시를 저장합니다. 입력 해시는 같은 입력을 다시 요약하지 않게 합니다.
- 실패를 기본값으로 저장하지 않습니다.
- 실행당 호출 상한과 일일 상한을 둡니다.
- 키가 없으면 그 작업만 skipped로 처리합니다.
- 응답 스키마를 검증합니다.
- 요약에는 "AI 생성" 표시와 원문 링크를 붙입니다.

### 7.3 통합 설계 제안 [추정·구현 안 함]

**공개 검색** (`GET /api/news?q=&tech=`)

- 내부 `contents`에서 title과 excerpt를 검색합니다.
- 기존 기술 필터와 AND로 결합합니다.
- 정렬은 기존 공개 정렬과 같습니다.
- 외부 API는 호출하지 않습니다(Q6).
- 검색어 길이와 문자 종류를 검증합니다.
- 구현 방법(`LIKE` 또는 MariaDB FULLTEXT/ngram)은 데이터량을 측정한 뒤 정합니다.
- 검색어는 저장하지 않습니다. 저장이 필요하면 별도 동의 정책을 둡니다.

**개인화 뉴스** (P5 범위, 별도 승인)

- 별도 엔드포인트(예: `/api/me/news/for-you`)와 별도 화면 영역을 씁니다.
- `profile_for_recommendation`이 `ready`일 때만 동작합니다.
- 관심 기술 ID ∩ 기사 기술 태그로 매칭합니다. 문자열 `ilike`는 쓰지 않습니다.
- `learner_type`은 쓰지 않습니다.
- `confident` 역량의 처리, 우선순위는 P5 문서 8절의 미결 사항을 따릅니다.

**검색어를 "관심사"로 자동 승격하지 않습니다.** 사용자가 직접 관심 기술로 추가할 때만 반영합니다.

## 10. 단계별 구현 계획

**각 단계는 별도 승인을 받은 뒤 구현합니다.** 이번에는 아무것도 구현하지 않았습니다.

### Phase A — RSS/API 수집 안정화

**선행 조건**

- 나머지 23개 호스트의 네트워크 허용 여부를 결정합니다.
- 실행 환경(로컬, 서버, CI)과 스케줄 방식을 결정합니다.

**변경 예상 파일**

- `app/integrations/http.py`: 429와 `Retry-After` 처리, 리다이렉트 상한과 호스트 검증
- `app/integrations/sources.py`: 항목 단위로 건너뛰고 집계, API URL 스킴 검증
- `app/jobs/runner.py`: 건너뛴 건수 기록
- 스케줄 정의(예: `docker-compose` 서비스 또는 cron 문서)

**테스트**

- `HttpFetcher` 단위 테스트: `httpx.MockTransport`로 200, 404, 429, 500, 크기 초과, 리다이렉트
- 어댑터 고정 응답 테스트에 필드 누락, `javascript:` URL 사례 추가
- 기존 수집 통합 테스트 유지

**복구**

- 코드 변경만이라 커밋 revert로 되돌립니다.
- 스키마를 바꾸면 Alembic downgrade를 씁니다(MariaDB DDL은 트랜잭션이 아니므로 사전 백업).

### Phase B — 실제 데이터 기반 기술 태깅 품질 평가

**선행 조건**

- Phase A를 마칩니다.
- 개발 DB에 실제 수집하는 것을 승인합니다.
- 라벨러와 라벨링 기준을 정합니다.

**변경 예상 파일**

- `review/tagging-eval/` (표본, 라벨, 기준 문서)
- 평가 스크립트(`scripts/` 또는 `app/jobs` 하위 명령)
- 별칭 YAML(`backend/content/technologies.yaml`) 개선안

**테스트**

- 평가 스크립트 단위 테스트(정확도, 재현율, F1 계산)
- 별칭을 바꾸면 기존 태깅 테스트로 회귀를 확인

**산출물**

- 소스별·기술별 정확도, 재현율, F1
- "본문이 필요한 소스" 후보 목록(Phase C 입력)

**복구**

- 평가 데이터는 파일이라 DB에 영향이 없습니다.
- 별칭 변경은 revert 후 재태깅합니다.

### Phase C — 필요한 소스에 한해 HTML 본문 추출 검토

**선행 조건**

- Phase B에서 본문이 필요하다는 근거가 나옵니다.
- 해당 소스의 robots.txt와 약관을 검토하고 사용자가 승인합니다.

**변경 예상 파일**

- 새 별도 작업(예: `app/jobs/enrich.py`)
- 소스 YAML에 `enrich: true` 같은 허용 플래그
- 결과 컬럼(마이그레이션)

**설계**

- 본문은 메모리에서만 다룹니다(Q8).
- 결과(기술 ID 등)만 저장합니다. 현재 `TAG_METHODS`는 `rule`/`llm`/`manual`뿐이라 새 method 값을 쓰려면 CHECK 제약 변경(마이그레이션)이 필요합니다.
- 기사 단위로 실패를 격리하고 호출 상한을 둡니다.

**테스트**

- 고정 HTML 스냅샷으로 추출 테스트
- 본문을 저장하지 않는다는 것을 테스트로 고정(컬럼 부재와 저장 값 검사)
- Phase B 라벨셋으로 전후 비교

**복구**

- 허용 플래그를 끄면 즉시 중단됩니다.
- 결과 행은 `method`로 구분해 삭제할 수 있습니다(삭제는 별도 승인).

### Phase D — AI 요약·분석 독립 모듈 설계

**선행 조건**

- 제품 목표에 요약 표시가 들어갑니다.
- 소스별로 요약 표시가 허용됩니다.
- 비용 상한과 키 관리 방식을 승인합니다.

**변경 예상 파일**

- 새 작업 모듈(예: `app/jobs/summarize.py`, `app/integrations/llm.py`)
- 결과 테이블(모델, 프롬프트 버전, 입력 해시, 상태, 생성 시각)
- 경계 테스트: 웹 앱이 LLM 모듈을 import하지 않음

**테스트**

- 가짜 LLM 클라이언트로 스키마 검증, 실패 시 상태 기록, 같은 입력의 재요약 방지, 상한
- 키가 없으면 skipped
- **실제 LLM 호출 없이 CI를 통과해야 합니다.**

**복구**

- 작업을 비활성화합니다.
- 화면은 요약이 없어도 정상 표시되도록 합니다(요약은 선택 필드).

### Phase E — 개인화 뉴스 추천 연결

**선행 조건**

- Phase B 수치가 허용 기준을 넘습니다. 기준은 사용자가 정합니다.
- P5 문서 8절의 미결 사항(`confident` 처리, 우선순위)을 결정합니다.
- 공개 검색(7.3)을 먼저 마칩니다.

**변경 예상 파일**

- `app/services/` 추천 서비스. 입력은 `profile_for_recommendation`만 씁니다.
- `/api/me/news/...` 라우트
- 프론트엔드에 별도 영역 추가

**테스트**

- P4 정책 테스트 확장:
  - OFF면 프로필을 읽지 않음
  - 공개 목록 정렬이 바뀌지 않음
  - `learner_type`을 쓰지 않음
- E2E

**복구**

- 라우트와 화면만 비활성화합니다.
- P4 데이터에는 영향이 없습니다.
