## 2. 비교 검토 (요청 8개 항목)

### 2.1 Career 학습 단원부터 추천할 때의 실질 가치
- 후보가 1개입니다. 관심 기술에 `python`이 있으면 항상 같은 1개 단원을, 없으면 아무것도 보여 주지 않습니다.
- 이것은 이미 공개 화면이 주는 정보입니다(트랙 목록, P2 "관련 학습", P3 목표의 연결 학습). **추가 가치가 거의 없습니다.**
- Python 2~5단원을 확정해도 후보는 5개이고 기술은 여전히 `python` 하나입니다. 순서를 정하는 것 말고는 "추천"이라고 할 판단이 없습니다.
- Career 단원은 우리가 통제하는 데이터라 품질 위험은 낮습니다. **콘텐츠가 늘어나면 첫 추천 대상으로 가장 적합합니다**(아래 6절 기준).

### 2.2 공개 단원 1개 상황에서 구현할 타당성
- 구현은 가능합니다(데이터 모델, P4 프로필 인터페이스, 단원-기술 연결이 모두 준비됨).
- 그러나 다음 이유로 **지금 구현하는 것은 권장하지 않습니다.**
  - 테스트 데이터로만 동작을 확인할 수 있어서, 추천 규칙(가중치, 다양성, 제외 규칙)의 적절성을 실제로 검증할 방법이 없습니다.
  - 빈 결과가 대부분인 기능을 노출하면 "개인화를 켰는데 아무것도 없다"는 경험이 됩니다.
  - 규칙을 지금 정해 두면, 콘텐츠가 들어온 뒤 다시 바꿔야 할 가능성이 큽니다.

### 2.3 추천 근거의 범위

| 근거 | 쓸 수 있는가 | 제안 |
|---|---|---|
| 관심 기술 (P4) | ON일 때만 | **1차 근거.** 기술 일치 = 단원-기술 연결 |
| 역량 자기 평가 (P4) | ON일 때만 | 보조(8절에서 수정): `learning`은 기초 단원 우선. `confident`라는 자기 평가만으로 단원을 제외하지 않음. 자기 평가라는 점을 이유 문구에 드러냄 |
| 학습 목표 (P3, C-1) | ON일 때만 **읽기** | 보조: 목표 대상(직무 core 기술, 기술, 트랙)의 단원. 목표를 바꾸지 않음 |
| 학습 진행 기록 | 읽기 | 제외 규칙에만 사용(완료 단원 제외, 진행 중 단원은 "이어보기"로 구분). 행동 기반 추론은 하지 않음 |
| 진로 후보 (P3) | – | v1에서 사용 안 함(목표와 중복되고, "저장"이 곧 관심이라는 보장이 없음) |
| 학습자 유형 | **사용 금지** (C-2) | 경계 테스트 유지 |
| Home·Dev 열람·클릭 | 수집 안 함 | 사용 안 함 |

### 2.4 개인화 OFF / 프로필 비어 있음

| 상태 | API (`GET /api/me/recommendations`) | 화면 |
|---|---|---|
| 게스트 | 401 | 추천 영역 없음 |
| OFF | `200 {enabled:false, items:[], reason:"personalization_off"}` | 추천 영역 없음 (설정 링크 한 줄만, 선택) |
| ON + 프로필 비어 있음 | `200 {enabled:true, items:[], reason:"profile_empty"}` | "관심 기술을 고르면 추천을 볼 수 있어요" + 설정 링크 |
| ON + 데이터 있음, 후보 없음 | `200 {..., items:[], reason:"no_candidates"}` | "아직 관심 기술에 맞는 학습이 없어요" (콘텐츠 부족을 그대로 표시) |
| ON + 결과 있음 | `200 {items:[{unit, reasons:[...]}]}` | 별도 "추천" 영역 |

판단은 P4의 `profile_for_recommendation()`만 사용합니다(OFF면 빈 값). 이 함수를 부르는 곳은 추천 모듈 하나로 한정하고, 경계 테스트로 강제합니다.

### 2.5 추천 이유의 설명 가능성
- 점수나 순위 모델 없이 **규칙 기반**으로 하고, 항목마다 이유 코드와 근거를 함께 돌려줍니다.
  - `interest_match{technology}` → "관심 기술 Python과 관련된 단원"
  - `goal_target{goal_title, target}` → "목표 '백엔드 개발자 되기'의 핵심 기술"
  - `skill_level{technology, level}` → "Python을 '배우는 중'으로 평가해 기초 단원부터 보여 줘요"
- 정렬 규칙도 공개 문서에 적습니다. 예: 목표 일치 > 관심 일치 > 카탈로그 순서, 같은 기술은 최대 N개.
- 이유가 하나도 없는 항목은 추천하지 않습니다.

### 2.6 기존 공개 콘텐츠 정렬 유지
- 추천은 **별도 인증 API와 별도 화면 영역**으로만 제공합니다. Home·Dev·Career 공개 목록 API와 순서는 바꾸지 않습니다.
- P1~P4의 동일성 테스트(게스트 = OFF = ON × 학습자 유형)를 그대로 유지하고, 추천 데이터가 있는 ON 사용자까지 확장합니다.

### 2.7 Phase 5 외부 수집·태깅 미검증 문제
- Home·Dev 추천은 (1) 실제 수집 성공과 (2) 태깅 정확도에 의존합니다. 둘 다 미확인입니다(수집 0건, ProxyError).
- 태깅이 틀리면 추천 이유("관심 기술 X 관련 기사")가 사실과 달라집니다. 이 상태로 Home·Dev 추천은 **하지 않습니다.**

### 2.8 착수 전 최소 콘텐츠 기준
6절에 정리합니다.

## 4. 추천 기능 상세 설계 (기준 충족 후 구현할 안)

### 4.1 모듈과 경계
- `services/recommendations.py`: 유일한 추천 모듈.
  - 읽기: `personalization.profile_for_recommendation`, 목표(읽기), 진행(완료 여부), 단원-기술 연결
  - 쓰기: **없음**
- `api/routes/me_recommendations.py`: `GET /api/me/recommendations?scope=career&limit=5`
- 경계 테스트:
  - 추천 모듈만 `profile_for_recommendation`을 호출합니다.
  - 추천 모듈은 어떤 테이블에도 쓰지 않습니다(쓰기 SQL 0건 테스트).
  - 공개 API 모듈은 추천 모듈을 import하지 않습니다.

### 4.2 규칙 (Career 단원 v1)
1. 후보: 공개 트랙의 공개 단원 중 완료하지 않은 것
2. 일치:
   - 관심 기술 ∩ 단원 기술
   - 목표 대상의 기술·트랙
   - (8절) `confident` 자기 평가는 제외 근거로 쓰지 않음
3. 정렬: (8절) 목표 일치와 관심 일치의 우선순위는 실데이터 확보 전까지 확정하지 않음. 진행 중 단원은 추천이 아니라 "이어보기"로 분리 → 카탈로그 순서
4. 다양성: 같은 기술 최대 2개, 전체 최대 5개
5. 이유: 일치 근거마다 이유 코드 1개 이상

### 4.3 화면
- Career 홈 "추천 학습" 영역: ON 사용자에게만, 이유 문구와 함께 표시합니다.
- 기존 섹션 순서와 내용은 그대로 둡니다.

### 4.4 테스트
- 상태별 응답(2.4)
- 이유 코드
- 완료 단원 제외
- 다양성 상한
- 쓰기 없음
- 학습자 유형 불변
- 공개 API 동일성(추천 데이터가 있는 ON 사용자 포함)
- 경계
- E2E(설정에서 관심 기술 → Career 홈 추천과 이유)

### 8.1 추천 종류별 선행 조건 분리

| 추천 | 데이터 출처 | 선행 조건 | 현재 |

| 직무 기반 추천 (목표가 직무인 경우) | 직무 파일 + 단원-기술 연결 | Career 조건 + 검증된 직무 6개 공개 + 각 직무 core 기술의 학습 연결 | 공개 직무 0 — 미충족 |

세 가지는 서로 독립적으로 열 수 있습니다. 예를 들어 Career 단원 추천은 Home·Dev 수집 문제와 무관하게 시작할 수 있습니다.

### 8.2 콘텐츠 목표 (잠정)
- 공개 단원 15개·기술 5개는 **잠정 품질 목표**로 유지합니다.
- 실제 판단은 "추천 후보 다양성"으로 조정합니다. 예: 관심 기술 3개를 고른 가상 사용자 프로필 20개 중 80% 이상이 서로 다른 단원을 2개 이상 받는가. 측정 스크립트로 계산해 보고합니다.

### 8.3 태깅 품질 평가
- precision만 보지 않고 **recall**과 **기술별 오탐·누락 사례**를 함께 평가합니다.
- 표본: news·dev 각 200건, 기술별로 층화 추출(상위 기술 + 무작위).
- 라벨링: 사람이 기술 집합을 직접 표시(복수 선택). 애매한 경우는 "판단 불가"로 따로 셉니다.
- 지표: 전체·기술별 precision/recall/F1, 오탐·누락 사례 목록(별칭 수정 근거로 사용).
- 기준(잠정): 추천에 쓰는 기술은 precision 0.8 이상, recall 0.6 이상. 미달 기술은 추천 근거에서 제외합니다.

### 8.4 역량 `confident`
- 자기 평가 `confident`만으로 입문 단원을 무조건 제외하지 않습니다.
- 쓰더라도 "이미 자신 있다고 평가한 기술입니다" 같은 이유 표시와 함께 순서를 뒤로 미는 정도로 한정하며, 실데이터 검토 후 결정합니다.

### 8.5 정렬 우선순위
- 목표 일치와 관심 기술 일치의 우선순위는 **실데이터 확보 전까지 확정하지 않습니다.**
- 초기 구현에서는 두 근거를 같은 등급으로 두고 카탈로그 순서를 쓰는 안을 기본값으로 합니다. 이유는 항목마다 따로 표시합니다.

### 8.6 완료·진행 중 단원
- 완료한 단원(`user_unit_progress.completed_at`)은 추천에서 제외합니다.
- 진행 중 단원은 추천 목록에 섞지 않고 기존 "이어서 학습하기"(요약 API의 `continue_unit`)로 구분합니다.

### 8.7 상태 분리
`personalization_off` / `profile_empty` / `no_candidates` / 결과 있음, 이렇게 네 가지를 API `reason` 코드와 화면 문구로 구분합니다(2.4).

### 8.8 공개 API 불변
공개 콘텐츠 API의 정렬과 응답은 바꾸지 않습니다. 기존 동일성 테스트를 추천 데이터가 있는 ON 사용자까지 확장해 강제합니다.

### 8.9 추천 이유
- 이유는 확인 가능한 근거로만 씁니다. 근거는 관심 기술, 목표 제목·대상, 자기 평가 수준, 단원-기술 연결입니다.
- 이유가 없는 항목은 내보내지 않습니다.
- 태깅 품질 기준(8.3)에 미달한 기술은 이유로 쓰지 않습니다.

### 8.10 읽기 전용
- 추천 API는 읽기 전용입니다. 쓰기 SQL 0건 테스트로 강제하고, 학습·XP·목표·후보·개인화 데이터에 영향을 주지 않습니다.
- 추천 노출·클릭 기록은 두지 않습니다(별도 결정 필요).
